Tổng quan và cách học

Bộ ghi chú về Docker và container cho người làm DevOps: từ khái niệm, build image, chạy container, mạng, lưu trữ, Compose đến bảo mật và xử lý sự cố. Đọc theo thứ tự thì mỗi trang dựa trên trang trước; cũng có thể tra riêng từng trang.

Đọc trước khi dùng

Đây là ghi chú tự học, tự soạn, không phải tài liệu chính thức của Docker, Inc. Tuỳ chọn dòng lệnh, giá trị mặc định và tính năng thay đổi theo phiên bản Docker Engine, Docker Desktop và BuildKit. Ghi chú không tra cứu trực tuyến nên có thể lỗi thời: hãy đối chiếu docs.docker.com và docker <lệnh> --help trước khi áp dụng, đặc biệt với lệnh có thể xoá dữ liệu.

Bạn sẽ làm được gì sau khi học xong

  • Giải thích container là gì ở mức Linux (namespace, cgroup, filesystem phân lớp) và khác máy ảo ở đâu.
  • Viết Dockerfile nhỏ, build nhanh nhờ cache, an toàn (multi-stage, non-root, không lộ bí mật).
  • Chạy, giới hạn, debug container; hiểu volume, bind mount và mạng bridge.
  • Dựng một stack nhiều dịch vụ bằng Compose, có healthcheck và tách môi trường dev/prod.
  • Áp dụng các biện pháp bảo mật cơ bản và xử lý được các sự cố hay gặp.

Liên quan tới các ghi chú khác

Docker dựa hoàn toàn vào các cơ chế của Linux: xem namespace, cgroups, dựng container từ đầu và mạng Linux trong ghi chú Linux. Khi cần chạy nhiều container trên nhiều máy, bước tiếp theo là Kubernetes.

Container là gì và kiến trúc Docker

Container là process Linux bị giới hạn về những gì nó thấy và dùng được, chạy từ một image chứa sẵn mọi thứ nó cần. Docker là bộ công cụ làm việc đó dễ dùng.

Vấn đề container giải quyết

"Chạy được trên máy tôi" xảy ra vì ứng dụng phụ thuộc vào hệ điều hành, thư viện, phiên bản runtime và cấu hình của máy. Container đóng gói ứng dụng cùng toàn bộ phụ thuộc userspace vào một image bất biến, để cùng một image chạy giống nhau trên laptop, CI và production.

Container ở mức Linux

Một container không phải là một "thứ" mà kernel biết. Nó là một process thông thường được bọc bởi:

  • Namespace: giới hạn những gì process nhìn thấy (cây PID, mount, mạng, hostname, user...). Xem Namespace.
  • cgroup: giới hạn những gì process dùng được (CPU, RAM, I/O, số process). Xem cgroups v2.
  • Filesystem phân lớp (overlayfs): các lớp chỉ đọc của image cộng một lớp ghi riêng của container.
  • Capabilities, seccomp, AppArmor/SELinux: giới hạn những gì process được phép làm.

Kết quả quan trọng: container dùng chung kernel với máy chủ. Vì vậy container Linux cần kernel Linux, khởi động trong mili giây, nhưng cô lập yếu hơn máy ảo.

Chuẩn OCI

Image, layer và digest

Image là chuỗi các lớp chỉ đọc cộng metadata, nhận diện bằng digest. Hiểu layer giải thích vì sao build nhanh hay chậm, vì sao image nặng, và vì sao tag không đáng tin.

Layer

Mỗi lệnh thay đổi filesystem trong Dockerfile (RUN, COPY, ADD) tạo một layer: một bản diff so với layer trước. Image là chồng các layer; container thêm một lớp ghi (writable) lên trên cùng. Docker dùng một storage driver (phổ biến nhất là overlay2, dựa trên overlayfs của Linux, xem Dựng container từ đầu) để hợp nhất các lớp thành một cây thư mục duy nhất.

   Container (lớp ghi)   <- thay đổi lúc chạy, mất khi xoá container
   ----------------------
   Layer 4: COPY app/ /app          } các lớp image:
   Layer 3: RUN pip install ...     } chỉ đọc,
   Layer 2: RUN apt-get install ... } chia sẻ giữa nhiều image
   Layer 1: base (debian-slim)      } và nhiều container

Hệ quả:

  • Chia sẻ: nhiều image dùng chung base chỉ lưu và tải layer chung một lần.
  • Copy-on-write: sửa một file ở lớp dưới thì file được sao chép lên lớp ghi rồi mới sửa. Ghi nhiều vào lớp ghi của container chậm và mất khi xoá container: dữ liệu bền phải ở volume.
  • Layer không bao giờ co lại: xoá file ở layer sau không làm image nhỏ đi, vì file vẫn nằm ở layer trước. Đây là lý do cần gom lệnh và dùng multi-stage.
  • Bí mật lộ trong layer: một file bí mật đã COPY vào rồi rm ở lệnh sau vẫn lấy ra được từ layer cũ.

Tag và digest

  • Tag (nginx:1.27) là tên có thể đọc được, nhưng có thể bị đổi để trỏ sang image khác (latest, thậm chí 1.27 khi có bản vá).
  • Digest (nginx@sha256:3f1a...) là mã băm của manifest: bất biến, nên đảm bảo chạy đúng image bạn đã thử.

Một tag đa kiến trúc trỏ tới một manifest list (index) gồm nhiều manifest, mỗi cái cho một nền tảng (linux/amd64, linux/arm64); Docker chọn đúng cái hợp với máy. Lỗi exec format error khi chạy thường do image sai kiến trúc.

Lệnh cần nhớ

docker pull nginx:1.27
docker image ls                              # image đã có; thêm --digests để thấy digest
docker image inspect nginx:1.27              # cấu hình: Env, Cmd, Entrypoint, danh sách layer
docker history nginx:1.27                    # từng layer: lệnh tạo ra và kích thước
docker image ls --filter dangling=true       # image không còn tag
docker image prune                           # xoá image dangling
docker save -o nginx.tar nginx:1.27          # xuất image (kèm layer) ra file
docker load -i nginx.tar
docker diff CONTAINER                        # các file đã đổi trong lớp ghi
docker export CONTAINER > fs.tar             # filesystem phẳng của container (không phải image)

docker save/load làm việc với image (giữ layer và tag, dùng để chuyển image sang máy không có mạng), còn docker export chỉ lấy filesystem phẳng của một container.

Đừng dùng docker commit để làm image

docker commit đóng băng container thành image, nhưng không ai biết nó được tạo thế nào và không tái tạo được. Hãy luôn mô tả bằng Dockerfile, để image có thể build lại từ mã nguồn.

Nhìn layer và lớp ghi
docker pull alpine:3.20

Dockerfile: tham chiếu các lệnh

Dockerfile là công thức build image. Trang này tóm tắt các lệnh, và những cặp dễ nhầm: CMD với ENTRYPOINT, COPY với ADD, ARG với ENV.

Ví dụ tối thiểu

# syntax=docker/dockerfile:1
FROM python:3.12-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
USER 10001
EXPOSE 8000
HEALTHCHECK --interval=30s --timeout=3s CMD python -c "import urllib.request,sys; urllib.request.urlopen('http://127.0.0.1:8000/health')" || exit 1
CMD ["python", "-m", "app"]

CMD, ENTRYPOINT và hai dạng viết

Mỗi lệnh RUN, CMD, ENTRYPOINT có hai dạng:

  • Exec form: CMD ["python", "app.py"]. Chạy chương trình trực tiếp, nó là PID 1 và nhận signal trực tiếp.
  • Shell form: CMD python app.py. Docker chạy /bin/sh -c "python app.py": PID 1 là sh, và nhiều shell không chuyển tiếp signal, nên docker stop không tắt êm được ứng dụng (xem Process và PID 1).

Cách dùng thường gặp:

Mục đíchViết
Chạy một ứng dụng, cho phép ghi đè lệnh khi debugCMD ["app", "--port", "8000"]
Image hoạt động như một công cụ (docker run img arg1 arg2)ENTRYPOINT ["tool"] và CMD ["--help"]
Cần xử lý biến môi trường rồi mới chạyScript entrypoint.sh kết thúc bằng exec "$@"

exec "$@" ở cuối script rất quan trọng: nó thay shell bằng ứng dụng, để ứng dụng trở thành PID 1 và nhận signal.

ARG và ENV

ARG chỉ tồn tại lúc build; ENV tồn tại cả trong image và container lúc chạy. Cả hai đều để lộ giá trị qua docker history và docker inspect, nên đừng truyền token hay mật khẩu bằng hai cách này (xem Dockerfile tốt về --mount=type=secret).

docker build . gửi toàn bộ thư mục hiện tại (build context) cho daemon. Context lớn làm build chậm và dễ chép nhầm file nhạy cảm vào image. Tạo .dockerignore:

Viết Dockerfile tốt: cache, multi-stage và buildx

Image tốt build nhanh, nhỏ, chạy bằng user thường và không chứa bí mật. Bốn kỹ thuật làm nên phần lớn khác biệt: thứ tự layer để tận dụng cache, multi-stage, BuildKit và quản lý bí mật.

Thứ tự layer và cache

Docker dùng lại một layer từ cache nếu lệnh và mọi thứ nó đọc không đổi. Khi một layer bị vô hiệu, mọi layer sau nó đều phải build lại. Vì vậy: đặt thứ ít đổi lên trên, thứ hay đổi (mã nguồn) xuống dưới.

# Xấu: sửa một dòng code là cài lại toàn bộ thư viện
COPY . .
RUN pip install -r requirements.txt

# Tốt: chỉ cài lại thư viện khi requirements.txt đổi
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .

Gom các lệnh dọn dẹp cùng một RUN với lệnh tạo ra rác, vì xoá ở layer sau không thu nhỏ image:

RUN apt-get update \
 && apt-get install -y --no-install-recommends curl ca-certificates \
 && rm -rf /var/lib/apt/lists/*

Multi-stage build

Dùng nhiều FROM: giai đoạn build có đầy đủ compiler, chỉ chép kết quả sang giai đoạn runtime nhỏ gọn.

# syntax=docker/dockerfile:1
FROM golang:1.23 AS build
WORKDIR /src
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 go build -o /out/app ./cmd/app

FROM gcr.io/distroless/static-debian12:nonroot
COPY --from=build /out/app /app
USER nonroot
ENTRYPOINT ["/app"]

Ví dụ Node.js (giai đoạn runtime dùng image nhỏ và user không phải root):

FROM node:22-alpine AS deps
WORKDIR /app
COPY package*.json ./
RUN npm ci --omit=dev

FROM node:22-alpine
WORKDIR /app
ENV NODE_ENV=production
COPY --from=deps /app/node_modules ./node_modules
COPY . .
USER node
CMD ["node", "server.js"]

docker build --target build . dừng ở một giai đoạn cụ thể (ví dụ để chạy test hoặc debug). Tên image nền (golang:1.23, distroless...) chọn phiên bản bạn dùng thật, đây chỉ là ví dụ.

BuildKit: cache mount, secret và buildx

BuildKit là engine build mặc định của Docker hiện nay (docker build và docker buildx build đều dùng nó). Một số tính năng cần dòng # syntax=docker/dockerfile:1 ở đầu Dockerfile.

Cache mount: giữ cache của trình quản lý gói giữa các lần build, mà không đưa vào image.

RUN --mount=type=cache,target=/root/.cache/pip \
    pip install -r requirements.txt

Secret mount: dùng bí mật lúc build (token tải thư viện riêng) mà không để lại trong layer hay docker history.

RUN --mount=type=secret,id=npm_token \
    NPM_TOKEN=$(cat /run/secrets/npm_token) npm ci
docker build --secret id=npm_token,src=$HOME/.npm_token -t web:dev .

Build đa nền tảng với buildx:

docker buildx create --use
docker buildx build --platform linux/amd64,linux/arm64 -t registry.example.com/web:1.4.2 --push .

Chia sẻ cache giữa các máy CI qua registry:

docker buildx build \
  --cache-from type=registry,ref=registry.example.com/web:buildcache \
  --cache-to   type=registry,ref=registry.example.com/web:buildcache,mode=max \
  -t registry.example.com/web:1.4.2 --push .

--progress=plain in toàn bộ output để xem lệnh nào chậm hay lỗi.

Registry, tag và chiến lược đặt tên

Registry là nơi image được lưu và phân phối. Cách bạn đặt tag quyết định việc triển khai có truy vết, lặp lại và quay lui được hay không.

Tên đầy đủ của một image

registry.example.com:5000 / team / web : 1.4.2
\_______ registry ______/   \ngăn/  \tên/ \tag/
  • Không ghi registry thì mặc định là Docker Hub (docker.io).
  • Không ghi tag thì mặc định là latest, không có nghĩa là bản mới nhất, chỉ là một tag tên như vậy.
  • Có thể thay tag bằng digest: web@sha256:....

  • Quét lỗ hổng ở registry (Harbor tích hợp Trivy) và quét lại định kỳ.
  • Sao chép giữa các registry (crane copy, skopeo copy) để mirror image đã duyệt.

Chạy container: docker run và vòng đời

docker run là lệnh dùng nhiều nhất. Nắm các tuỳ chọn chính và vòng đời container giúp bạn điều khiển và debug mà không phải đoán.

Vòng đời

   docker create            docker start          docker stop / kill, hoặc tiến trình tự thoát
 (image) ---------> created ------------> running ------------------------------------> exited
                                            |   ^                                         |
                                  pause     |   | unpause                                 | docker start
                                            v   |                                         | (chạy lại)
                                            paused                                        v
                                                                                       running
                    docker rm: xoá container (từ created hoặc exited) -> mất lớp ghi và log

docker run = docker create + docker start (+ attach nếu không có -d). Container đã thoát (exited) vẫn còn trên đĩa cùng lớp ghi và log cho tới khi docker rm; vì thế docker ps -a hiện cả container đã dừng.

Khởi động lại tự động che lỗi: container crash liên tục sẽ lặp (Docker tăng dần khoảng chờ). Luôn kèm giám sát và xem RestartCount.

Dừng container

docker stop gửi SIGTERM tới PID 1, chờ 10 giây (đổi bằng -t), rồi gửi SIGKILL. docker kill gửi SIGKILL ngay (hoặc -s signal khác). Muốn tắt êm thì ứng dụng phải nhận và xử lý SIGTERM: dùng exec form hoặc --init (xem Dockerfile).

Vòng đời bằng tay

Giới hạn tài nguyên

Không giới hạn thì một container hỏng có thể làm cạn CPU, RAM hay số process của cả máy. Docker dịch các tuỳ chọn thành cgroup, nên hành vi chính là hành vi của kernel.

Các giới hạn

--memory-swapTrần RAM + swap (đặt bằng --memory để tắt swap cho container)
--memory-reservationMức "mềm", kernel thu hồi bộ nhớ khi máy thiếu

CPU và bộ nhớ vượt trần khác nhau

Giống phần giải thích ở Tài nguyên trong Kubernetes: CPU vượt trần thì bị throttle (làm chậm), còn bộ nhớ vượt trần thì bị OOM kill (exit code 137). Một container OOM không phải máy hết RAM mà là chính cgroup của nó đầy.

docker inspect -f 'oom={{.State.OOMKilled}} exit={{.State.ExitCode}}' api
docker stats --no-stream api
ID=$(docker inspect -f '{{.Id}}' api)
cat /sys/fs/cgroup/system.slice/docker-$ID.scope/memory.max      # cgroup v2, driver systemd
cat /sys/fs/cgroup/system.slice/docker-$ID.scope/cpu.max

Đường dẫn cgroup phụ thuộc cgroup driver và phiên bản; xem cgroups v2. Vài lưu ý:

  • docker stats hiện CPU % theo core: 200% nghĩa là dùng hai core đầy. MEM USAGE thường không tính page cache, nên con số có thể thấp hơn những gì memory.current của cgroup báo.
  • Ứng dụng có runtime tự quản lý bộ nhớ (JVM, Node, Go): đặt heap thấp hơn giới hạn container, vì còn bộ nhớ ngoài heap. Các bản runtime mới nhận biết giới hạn cgroup, nhưng nên kiểm chứng với phiên bản bạn dùng.
  • Đặt giới hạn bộ nhớ quá sát mức dùng thật sẽ gây OOM vào lúc cao điểm; cần có đệm.

Thói quen tốt

  • Mọi container production đều có giới hạn bộ nhớ và --pids-limit.
  • Đo mức dùng thật trước khi đặt số (docker stats, Prometheus + cAdvisor).
  • Với Compose, giới hạn khai báo trong deploy.resources.limits (xem Compose thực tế).

Volume, bind mount và tmpfs

Lớp ghi của container mất khi container bị xoá. Dữ liệu cần giữ phải nằm ở nơi khác: volume do Docker quản lý, thư mục của host gắn vào (bind mount), hoặc RAM (tmpfs).

Ba cách lưu dữ liệu

LoạiDữ liệu nằm ở đâuDùng khiLưu ý
Volume (named)/var/lib/docker/volumes/NAME/_data, Docker quản lýDữ liệu ứng dụng cần giữ (database, upload)Cách được khuyên cho dữ liệu bền; độc lập với đường dẫn host
Bind mountThư mục bạn chỉ định trên hostMã nguồn khi phát triển, file cấu hìnhPhụ thuộc cấu trúc thư mục host; vấn đề quyền; có thể sửa file host từ container

docker volume create pgdata
docker run -d --name db -v pgdata:/var/lib/postgresql/data -e POSTGRES_PASSWORD=secret postgres:16

docker run -d --tmpfs /tmp:rw,size=64m myorg/app

Hai cú pháp:

-v pgdata:/var/lib/postgresql/data                         # ngắn gọn
--mount type=volume,source=pgdata,target=/var/lib/postgresql/data     # tường minh
--mount type=bind,source="$PWD/conf",target=/etc/app,readonly

--mount báo lỗi nếu đường dẫn nguồn của bind mount không tồn tại, còn -v sẽ tự tạo thư mục rỗng (thường là thư mục thuộc root), nguồn gốc của nhiều lỗi quyền khó hiểu.

Vòng đời và các cái bẫy

  • Volume tồn tại sau khi xoá container (trừ volume ẩn danh khi dùng docker rm -v). Để dọn: docker volume ls, docker volume rm NAME, docker volume prune (xoá volume không có container nào dùng: cẩn thận).
  • Volume ẩn danh sinh ra từ lệnh VOLUME trong Dockerfile khi bạn không gắn volume có tên: chúng chất đống theo từng lần docker run. Nên gắn volume có tên cho dữ liệu cần giữ.
  • Khởi tạo nội dung: khi gắn volume trống vào một thư mục đã có dữ liệu trong image, Docker chép dữ liệu image vào volume lần đầu. Bind mount thì che nội dung của image bằng nội dung thư mục host.
  • Quyền và UID: file do process trong container tạo ra mang UID của process đó (thường không trùng user trên host). Bind mount thư mục mà UID không khớp sẽ lỗi permission denied. Cách xử lý: chạy container với --user "$(id -u):$(id -g)", hoặc chown thư mục cho UID của ứng dụng, hoặc dùng volume có tên.
  • SELinux (RHEL, Fedora): thêm hậu tố :z (chia sẻ) hoặc :Z (riêng) vào bind mount, ví dụ -v $PWD/conf:/etc/app:ro,z.
  • Hiệu năng trên Docker Desktop: bind mount qua VM chậm hơn volume; ưu tiên volume cho thư mục nặng I/O (node_modules, database).

Sao lưu và khôi phục volume

# Sao lưu volume ra tệp tar
docker run --rm -v pgdata:/data:ro -v "$PWD":/backup alpine tar czf /backup/pgdata.tgz -C /data .
# Khôi phục vào volume mới
docker volume create pgdata2
docker run --rm -v pgdata2:/data -v "$PWD":/backup alpine tar xzf /backup/pgdata.tgz -C /data

Chép file của database đang chạy cho bản sao không nhất quán: với database, dùng công cụ riêng (pg_dump, mysqldump) hoặc dừng container trước khi sao lưu. Xem thêm Backup, rsync.

Publish cổng

Container ở bridge có IP riêng, bên ngoài không truy cập được. -p thiết lập luật DNAT để chuyển cổng của host vào container:

docker run -d -p 8080:80 nginx                    # mọi giao diện của host, cổng 8080 -> 80
docker run -d -p 127.0.0.1:8080:80 nginx          # chỉ truy cập từ chính máy
docker run -d -p 8080:80/udp myorg/dns            # UDP
docker run -d -P nginx                            # cổng host ngẫu nhiên cho mọi cổng EXPOSE
docker port NAME
Publish cổng mà không chỉ định địa chỉ là mở ra mọi giao diện

-p 5432:5432 cho phép cả mạng kết nối vào database, và vì Docker tự chèn luật iptables riêng, nó bỏ qua ufw và nhiều cấu hình firewall bạn tưởng đang bảo vệ. Với dịch vụ chỉ dùng nội bộ: không publish, hoặc bind 127.0.0.1, hoặc nối qua mạng Docker. Luật tuỳ chỉnh đặt ở chain DOCKER-USER.

EXPOSE trong Dockerfile không mở cổng, chỉ là ghi chú.

Truy cập host và DNS

  • Từ container gọi ra máy chủ: trên Docker Desktop dùng host.docker.internal; trên Linux thêm --add-host=host.docker.internal:host-gateway.
  • DNS của container lấy từ cấu hình của host, hoặc đặt riêng: --dns 10.0.0.2, --dns-search example.internal.
  • Trong mạng người dùng tạo, 127.0.0.11 là resolver nhúng của Docker: tên container và alias (--network-alias) được phân giải ở đó, các tên khác chuyển cho DNS ngoài.

Docker Compose cơ bản

Compose mô tả cả một ứng dụng nhiều container (dịch vụ, mạng, volume) trong một file YAML và điều khiển nó bằng vài lệnh. Phù hợp để phát triển, kiểm thử và chạy trên một máy.

Một file compose.yaml

services:
  web:
    image: nginx:1.27-alpine
    ports:
      - "127.0.0.1:8080:80"
    depends_on:
      app:
        condition: service_healthy
  app:
    build: ./app
    environment:
      DATABASE_URL: postgres://app:${DB_PASSWORD}@db:5432/app
    depends_on:
      db:
        condition: service_healthy
    healthcheck:
      test: ["CMD", "python", "-c", "import urllib.request; urllib.request.urlopen('http://127.0.0.1:8000/health')"]
      interval: 10s
      timeout: 3s
      retries: 5
  db:
    image: postgres:16
    environment:
      POSTGRES_USER: app
      POSTGRES_PASSWORD: ${DB_PASSWORD}
      POSTGRES_DB: app
    volumes:
      - pgdata:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U app -d app"]
      interval: 5s
      retries: 10

volumes:
  pgdata:

Các khoá cấp cao nhất: services, networks, volumes, configs, secrets. Khoá version: ở đầu file đã lỗi thời trong Compose hiện nay và có thể bỏ. Compose tự tạo một mạng riêng cho dự án (nên các dịch vụ gọi nhau bằng tên: db, app) và đặt tên tài nguyên theo TÊNDỰÁN-dịch-vụ-số (tên dự án mặc định là tên thư mục).

Biến và file môi trường

  • Thay thế biến trong chính file YAML: ${DB_PASSWORD} lấy từ môi trường shell hoặc từ file .env cùng thư mục với compose.yaml. Giá trị mặc định: ${PORT:-8080}, bắt buộc: ${DB_PASSWORD:?cần đặt DB_PASSWORD}.
  • Biến cho container: environment: (khai báo trực tiếp) hoặc env_file: [app.env] (nạp từ file).

Hai thứ này khác nhau: .env phục vụ việc thay thế trong YAML, còn env_file đưa biến vào container. Đừng commit file chứa bí mật; xem Compose thực tế về secrets.

depends_on và healthcheck

depends_on mặc định chỉ bảo đảm thứ tự khởi động, không phải "đã sẵn sàng". Muốn đợi dịch vụ phụ thuộc thật sự sẵn sàng, đặt healthcheck cho nó và dùng condition: service_healthy. Ứng dụng vẫn nên tự thử kết nối lại khi database chưa sẵn sàng, vì database có thể khởi động lại sau này.

Compose trong thực tế: dev, prod và bí mật

Một file Compose dùng được cho cả phát triển lẫn triển khai nhỏ nếu bạn tách phần khác nhau, quản lý bí mật đúng cách và hiểu giới hạn của Compose.

Tách cấu hình theo môi trường

Compose tự đọc compose.yaml rồi gộp compose.override.yaml nếu có (thường dùng cho dev). Với các môi trường khác, chỉ định rõ các file:

# compose.yaml : phần chung
services:
  app:
    image: registry.example.com/team/app:${TAG:-dev}
    restart: unless-stopped

# compose.override.yaml : chỉ cho dev, tự gộp
services:
  app:
    build: ./app
    volumes: ["./app:/src"]
    environment: {DEBUG: "1"}
    ports: ["127.0.0.1:8000:8000"]

# compose.prod.yaml : cho production
services:
  app:
    deploy:
      resources:
        limits: {cpus: "1.0", memory: 512M}
    logging:
      driver: json-file
      options: {max-size: "10m", max-file: "3"}
docker compose up -d                                            # dev: compose.yaml + override
docker compose -f compose.yaml -f compose.prod.yaml up -d       # prod

Dùng docker compose config để xem kết quả gộp. Khi gộp, giá trị đơn bị ghi đè và danh sách được nối thêm.

Tái sử dụng bằng YAML anchor và extension field

x-common: &common
  restart: unless-stopped
  logging: {driver: json-file, options: {max-size: "10m", max-file: "3"}}
  security_opt: ["no-new-privileges:true"]

services:
  api:    {<<: *common, image: myorg/api:1.4.2}
  worker: {<<: *common, image: myorg/worker:1.4.2}

Bí mật

Biến môi trường dễ lộ (docker inspect, log, file crash). Compose hỗ trợ secrets, gắn dưới dạng file trong /run/secrets/TÊN:

services:
  db:
    image: postgres:16
    environment:
      POSTGRES_PASSWORD_FILE: /run/secrets/db_password
    secrets: [db_password]
secrets:
  db_password:
    file: ./secrets/db_password.txt        # đặt ngoài Git, quyền 600

Nhiều image chính thức hỗ trợ hậu tố _FILE cho các biến nhạy cảm. Với bí mật thật của production, dùng công cụ quản lý bí mật (Vault, dịch vụ của cloud) thay vì file trên đĩa.

Compose không phải là gì

Compose chạy trên một máy: không có tự phục hồi khi máy chết, không tự rải container qua nhiều máy, không rolling update đúng nghĩa. Dùng cho phát triển, CI, và dịch vụ nhỏ chấp nhận được rủi ro một máy. Khi cần nhiều máy, tự phục hồi và triển khai không gián đoạn, chuyển sang Kubernetes (công cụ kompose giúp chuyển file Compose thành manifest, nhưng kết quả cần được rà soát và sửa tay).

Gộp cấu hình hai môi trường

Bảo mật container

Container cô lập yếu hơn máy ảo vì dùng chung kernel. Bảo mật nghĩa là thu hẹp những gì process trong container làm được và những gì nó chạm tới được, theo nhiều lớp, để một lớp hỏng không kéo theo cả máy chủ.

Mô hình mối đe doạ

Giả sử kẻ tấn công đã chạy được code trong container của bạn (qua lỗ hổng ứng dụng hay thư viện). Câu hỏi là: họ làm gì được tiếp? Nếu container chạy root, có nhiều capability, mount docker.sock hay chạy --privileged, câu trả lời thường là "chiếm cả máy chủ". Mục tiêu của các biện pháp dưới đây là làm cho câu trả lời trở thành "gần như không gì cả".

Chế độ rootless và user namespace

Mặc định daemon chạy bằng root, nên thoát khỏi container thường nghĩa là có root trên host. Hai cách giảm rủi ro:

  • Rootless mode: chạy cả daemon và container bằng một user thường (dockerd-rootless-setuptool.sh install). Đổi lại có một số hạn chế (mạng, cổng dưới 1024, một số storage driver).
  • userns-remap: ánh xạ root trong container thành một UID không có quyền trên host ("userns-remap": "default" trong daemon.json).

Podman chạy rootless theo mặc định, xem Hệ sinh thái.

Bí mật

  • Không đặt bí mật vào image (COPY, ENV, ARG): chúng nằm vĩnh viễn trong layer và docker history.
  • Biến môi trường dễ lộ qua docker inspect, /proc/PID/environ, log và báo cáo lỗi. Ưu tiên file bí mật (/run/secrets), và Vault hoặc dịch vụ bí mật của cloud cho production. Xem Compose thực tế.
  • Dùng secret mount của BuildKit cho bí mật lúc build (Dockerfile tốt).

Chuỗi cung ứng image

Chạy image là chạy code của người khác. Quét lỗ hổng (Trivy, Grype), sinh SBOM, ký image bằng cosign và xác minh khi triển khai, ghim digest, và dùng registry nội bộ làm nguồn duy nhất. Chi tiết và ví dụ ở trang Bảo mật chuỗi cung ứng image.

Bảo vệ daemon và host

  • Daemon lắng nghe qua Unix socket. Không bao giờ mở TCP 2375 không xác thực ra mạng: ai kết nối được đều chiếm được máy. Nếu bắt buộc phải truy cập từ xa, dùng TLS hai chiều (cổng 2376) hoặc SSH (DOCKER_HOST=ssh://user@host).
  • Group docker tương đương quyền root: cấp hạn chế.
  • Cập nhật Docker, runc, và kernel: nhiều lỗ hổng thoát container nằm ở các thành phần này.
  • Tham khảo CIS Docker Benchmark; công cụ docker-bench-security kiểm tra tự động nhiều mục.
So sánh mặc định và đã cứng hoá
docker run --rm alpine id                                   # uid=0(root)
docker run --rm alpine sh -c 'grep Cap /proc/self/status'   # capability mặc định
docker run --rm --user 10001:10001 --cap-drop=ALL --read-only alpine sh -c 'id; grep Cap /proc/self/status; touch /x'
docker run --rm --cap-drop=ALL alpine ping -c1 127.0.0.1    # ping cần CAP_NET_RAW: thất bại
docker run --rm --cap-drop=ALL --cap-add=NET_RAW alpine ping -c1 127.0.0.1

daemon.json

Cấu hình daemon ở /etc/docker/daemon.json (Linux), cần sudo systemctl restart docker để áp dụng (hầu hết các mục).

Log

Mỗi container có log là thứ ứng dụng ghi ra stdout và stderr (không phải file trong container). Docker thu và lưu theo logging driver:

DriverGhi chú
json-file (mặc định)Lưu file JSON trên host; không xoay vòng nếu không đặt max-size; docker logs đọc được
localĐịnh dạng gọn hơn, xoay vòng mặc định; docker logs đọc được
journaldVào journal của systemd; docker logs đọc được
syslog, fluentd, gelf, awslogs, splunk...Đẩy thẳng ra hệ thống ngoài; với một số driver docker logs không đọc được nữa

Đặt theo từng container: docker run --log-opt max-size=10m --log-opt max-file=3 .... Ứng dụng nên ghi log ra stdout/stderr, và dùng agent (Fluent Bit, Promtail, OTel) hoặc log driver để gom về nơi tập trung.

Giám sát

docker stats                                 # CPU, RAM, mạng, I/O theo thời gian thực
docker events --filter event=die             # container nào vừa chết
docker ps --format '{{.Names}}: {{.Status}}' # có "(healthy)" hoặc "(unhealthy)" nếu có healthcheck
docker inspect -f '{{.State.Health.Status}}' web

Cho nhiều container: cAdvisor xuất metric từng container cho Prometheus; cảnh báo theo container_memory_working_set_bytes, số lần restart, và oom_kill.

Dọn dẹp

docker system df                             # đang chiếm bao nhiêu
docker container prune                       # container đã dừng
docker image prune                           # image dangling; thêm -a để xoá mọi image không dùng
docker builder prune                         # cache build
docker volume prune                          # volume không có container nào dùng
docker system prune                          # gộp nhiều thứ ở trên (không gồm volume)
docker system prune -a --volumes             # rất mạnh: xoá cả volume không dùng
prune --volumes xoá dữ liệu

docker volume prune và docker system prune --volumes xoá volume không có container nào đang dùng: một volume của container đã dừng cũng bị tính là "không dùng" và mất dữ liệu. Kiểm tra bằng docker volume ls trước, và đặt lịch dọn image/cache (không phải volume) cho máy CI.

Xử lý sự cố

Các sự cố Docker hay gặp, theo khung: triệu chứng, cách kiểm tra theo thứ tự, nguyên nhân, cách sửa. Hầu hết đều được trả lời bởi docker logs, docker inspect và hiểu biết về Linux bên dưới.

Quy trình chung

  1. docker ps -a: container ở trạng thái nào, thoát khi nào, mã thoát?
  2. docker logs --tail 100 NAME: ứng dụng nói gì trước khi chết?
  3. docker inspect NAME: State (ExitCode, OOMKilled, Error), cấu hình thật (Env, Mounts, Networks).
  4. Tái hiện bằng tay: docker run --rm -it --entrypoint sh IMAGE.
  5. Nếu liên quan tới Linux bên dưới: docker events, dmesg, ss, nsenter.

Kịch bản 1: Container thoát ngay sau khi chạy

docker ps -a --filter name=app
docker logs app
docker inspect -f '{{.State.ExitCode}} {{.State.OOMKilled}} {{.State.Error}}' app
docker run --rm -it --entrypoint sh IMAGE

Kịch bản 2: Cổng đã publish nhưng không truy cập được

docker port web
docker exec web ss -tlnp                      # (nếu image có ss) ứng dụng nghe trên địa chỉ nào?
sudo iptables -t nat -L DOCKER -n
curl -v http://127.0.0.1:8080
  • Ứng dụng nghe 127.0.0.1 bên trong container thì luồng publish không tới được: phải nghe 0.0.0.0.
  • Sai thứ tự host:container trong -p.
  • Firewall của host hoặc security group của cloud chặn; hoặc -p 127.0.0.1:... nên máy khác không vào được.
  • Đang kiểm tra từ container khác nhưng dùng cổng host thay vì cổng container (trong cùng mạng Docker gọi thẳng tên:cổng-container).

Kịch bản 3: Container không gọi được container khác bằng tên

docker network inspect appnet
docker exec app cat /etc/resolv.conf          # nameserver 127.0.0.11?
docker exec app getent hosts db

Thường do ở bridge mặc định (không có DNS theo tên) hoặc khác mạng; sửa bằng cách tạo mạng riêng và nối cả hai (Mạng). Trong Compose, hai dịch vụ chỉ thấy nhau nếu cùng một mạng.

Kịch bản 4: Permission denied trên volume hoặc bind mount

docker exec app id
docker exec app ls -ln /data
ls -ln ./data                                  # UID/GID trên host

UID của ứng dụng trong container không có quyền trên thư mục. Sửa: chown thư mục cho đúng UID, chạy --user khớp, dùng volume có tên; trên RHEL/Fedora thêm :z/:Z cho SELinux (Volume). Nếu thư mục bind mount chưa tồn tại và dùng -v, Docker tạo nó thuộc root.

Kịch bản 5: no space left on device

docker system df
sudo du -xh --max-depth=1 /var/lib/docker | sort -h | tail
sudo ls -lh $(docker inspect -f '{{.LogPath}}' NAME)
df -h; df -i

Thủ phạm thường gặp: log json-file không xoay vòng, image và layer cũ, cache build, volume ẩn danh, container đã dừng. Dọn bằng docker system prune (xem cảnh báo về volume ở Daemon và log), và đặt max-size cho log. Kiểm tra cả df -i (hết inode).

Hệ sinh thái: Podman, containerd và Kubernetes

Docker không phải là cách duy nhất để chạy container. Biết bản đồ các thành phần giúp bạn đọc tài liệu Kubernetes, chọn công cụ phù hợp và không bị bất ngờ khi môi trường khác Docker.

Docker và Kubernetes

  • Kubernetes không nói chuyện với Docker mà nói với một runtime qua CRI (Container Runtime Interface). Các runtime phổ biến là containerd và CRI-O. Từ Kubernetes 1.24, dockershim (lớp tích hợp trực tiếp Docker) đã bị gỡ.
  • Điều này không làm image build bằng Docker ngừng chạy: image tuân thủ OCI nên chạy tốt trên mọi runtime.
  • Điểm khác trong vận hành: trên node Kubernetes không còn lệnh docker; dùng crictl (hoặc nerdctl) để xem container trên node.
DockerTương đương trên node Kubernetes

docker logscrictl logs hoặc kubectl logs

Kiến thức về image, layer, mạng bridge, volume, giới hạn tài nguyên và bảo mật trong ghi chú này áp dụng trực tiếp ở Kubernetes: xem Pod, Tài nguyên và Probe, tắt êm.

Công cụ phát triển

  • Docker Desktop: tiện (GUI, Kubernetes tích hợp, WSL2) nhưng có điều khoản cấp phép cho tổ chức lớn: hãy kiểm tra.
  • Lựa chọn thay thế trên máy cá nhân: Podman Desktop, Rancher Desktop, Colima (macOS/Linux), hoặc cài Engine trong WSL2/VM.
  • Cụm Kubernetes cục bộ: kind, k3d, minikube.

Đi tiếp

Sau Docker: chạy trên nhiều máy với Kubernetes, mô tả hạ tầng bằng mã (IaC: Terraform và Ansible), và tự động hoá build và phát hành (CI/CD).
